# Redis Online Shop 简历亮点

## 项目定位

Redis Online Shop 是一个基于 Spring Boot 3、Redis、MySQL、MyBatis-Plus 的商城后端项目，围绕“JWT 鉴权 - 商品缓存 - 购物车 - 幂等结算 - 库存扣减 - 订单落库 - 消息队列异步消费”构建完整交易链路。

## 可直接写进简历的项目描述

基于 Spring Boot 3 + Redis + MySQL 设计并实现在线商城后端系统，支持 JWT 鉴权、Redis Session、商品缓存、购物车、订单结算、库存扣减、订单事件消息队列、接口限流、请求追踪和健康检查。结算链路引入 Redis 分布式锁与 Idempotency-Key 幂等机制，解决并发结算和重复提交问题；订单创建后通过 Redis Stream 发布领域事件，并使用消费者组异步消费、ACK 和死信队列处理异常消息，降低核心交易链路耦合度。

## 技术亮点

- 认证鉴权：实现 HMAC-SHA256 JWT，支持 `jti`、`exp`、签名校验、Redis 黑名单登出，同时兼容 Redis Session。
- 高并发结算：使用 Redis SET NX + TTL + Lua 原子释放实现分布式锁，保护同一用户结算链路。
- 幂等控制：使用 `Idempotency-Key` 将一次结算请求与最终订单绑定，重复请求直接返回原订单。
- 库存安全：使用 MySQL 条件更新 `stock = stock - ? WHERE stock >= ?` 避免超卖。
- 消息队列：使用 Redis Stream 发布 `ORDER_CREATED` 事件，消费者组异步消费，成功 ACK，失败进入 DLQ。
- 缓存设计：使用 Redis 缓存商品、用户、会话、购物车、幂等结果和 JWT 黑名单。
- 流量治理：使用 Redis 固定窗口限流保护 `/api/**`，突发流量返回 HTTP 429。
- 性能优化：使用定时任务预热热门商品和商品列表缓存。
- 可观测性：统一异常响应、请求 traceId、Actuator 健康检查和指标暴露。
- 测试保障：使用 JUnit 5 + Mockito 覆盖 JWT、用户、商品、购物车、订单、幂等结算等核心逻辑。

## 面试可讲的问题与答案

### 为什么 JWT 和 Session 都保留？

JWT 适合无状态接口鉴权，便于水平扩展；Redis Session 适合服务端主动控制会话。项目同时支持两种方式：新接口可以使用 `Authorization: Bearer <token>`，也兼容原来的 `X-Session-ID`，体现平滑升级能力。

### JWT 如何实现退出登录？

JWT 天然无状态，服务端不能直接删除已发出的 token。项目在 JWT 中加入 `jti`，退出登录时将 `jti` 写入 Redis 黑名单，TTL 设置为 token 剩余有效期。请求进入系统时先验签，再检查黑名单，从而支持主动登出。

### 为什么要做结算幂等？

用户可能因为网络抖动、浏览器重试、前端重复点击产生多次结算请求。如果没有幂等控制，可能会重复扣库存、重复生成订单。项目通过 `Idempotency-Key` 将一次业务请求和最终订单绑定：首次请求成功后把订单结果缓存到 Redis，相同 key 再次请求时直接返回原订单。

### 为什么还需要分布式锁？

幂等键解决的是“同一个请求重复提交”，分布式锁解决的是“同一用户多个不同请求同时结算”。锁粒度是 `lock:checkout:{userId}`，保证同一用户购物车同一时刻只有一个结算流程。

### 为什么用 Redis Stream 做消息队列？

订单创建后，通知、积分、优惠券、库存流水、数据分析等逻辑不应该都塞进结算事务。Redis Stream 可以把 `ORDER_CREATED` 事件发布出去，由消费者组异步处理；处理成功 ACK，处理失败进入死信队列，便于补偿和排查。

### 库存如何避免超卖？

库存扣减没有使用“先查库存再更新”的方式，而是通过数据库条件更新完成：

```sql
UPDATE product
SET stock = stock - ?
WHERE id = ? AND stock >= ?
```

只有库存足够时 SQL 才会影响行数，服务层根据影响行数判断扣减是否成功。
